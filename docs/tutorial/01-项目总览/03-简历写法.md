# 简历写法

> **让简历经得起追问。** 简历里出现的每一个数字和方法名，都要能落到代码和评测报告上。

本文用于投递前写简历条目。核对基准是 `eval/results/final_20261109_000831/report.md`（2026-11-09 测量）。

---

## 一、项目怎么命名、怎么一句话介绍

- **项目名称**：代码仓库 Coding Agent（基于开源项目二次开发）
- **一句话**：基于 LangGraph 的代码仓库 Agent，能自己读代码、改文件、跑测试；我把工具调用改成原生 function calling，并搭建了可复现的评测框架，成功率从 58.3% 提升到 97.2%。

"基于开源项目二次开发"一定要写。原项目公开在 GitHub 上，主动说明，面试官问"哪些是你做的"时你就能直接回答；被面试官自己查出来，就很被动了。

## 二、数字核对

写进简历的每个数字，都必须带上下面这些口径。

| 数字 | 含义 | 口径 |
| --- | --- | --- |
| 58.3% → 97.2% | 总成功率，v0 → v1 | 12 个任务 × 每个 3 次 = 36 次运行；模型 DeepSeek V4.1-Flash（硅基流动），关闭 thinking |
| 37.5% → 100% | 多文件仓库任务成功率 | 8 个 minishop 任务 × 3 次 = 24 次运行 |
| 15 次 → 0 | 因格式问题中止的运行次数 | 每种配置各 36 次运行；v0 的 15 次全部是 DSML 标记泄漏 |
| 约 3.3 万 token | 每个成功任务的 token 成本 | v0 33.8k，v1 33.0k，v2 31.7k，基本持平 |
| 3 道 | 原数据集里的坏题 | 1 道答案已经写在题目里，2 道测试缺少导入、不可能通过 |
| 4 处 | 修复的安全漏洞 | `conda run`、前缀匹配、黑名单大小写、密钥可读/可泄露 |
| 38 个 | 单元测试 | 用按剧本回复的假模型，不调用真实接口 |

**不能写的数字：**

- 不能写"测试驱动验证提升了成功率"。它在这批任务上一次都没被触发，v2 和 v1 的成功率相同。只能说"加了测试驱动验证作为兜底"。
- 不能写"成本降低"。单次运行的 token 其实多了约 60%，只是按每个成功任务算基本持平。
- 不要引用原项目 README 里的 SFT 数字（例如 JSON 合法率 0% → 94.6%）。你没有做 SFT，而且那组数字主要是评测设置造成的。

## 三、可以直接使用的条目

格式：**动作 + 技术 + 可量化结果**。

### 精简版（3 条）

- 基于开源项目二次开发代码仓库 Agent（LangGraph + OpenAI 兼容接口），将工具调用从"prompt 约定 JSON + 文本解析"改为原生 function calling（JSON Schema、结构化 tool_calls、多轮 tool 消息）；在自建的 12 任务、108 次运行评测中，成功率从 58.3% 提升至 97.2%，多文件仓库任务从 37.5% 提升至 100%。
- 定位原版的主要失败原因：请求未带 tools 参数时，DeepSeek V4.1-Flash 会把原生工具调用标记（DSML）输出到文本中，导致解析失败、任务中止（v0 失败的 15 次全部如此）；改造后格式类中止降为 0。
- 搭建可复现的评测框架：向正确代码注入 bug 来生成任务，并自动校验每个任务"可解且非平凡"（查出原数据集 3 道坏题）；判定时恢复原始测试并加入隐藏测试；用三种配置逐项消融，统计成功率、步数、token 和耗时。

### 完整版（再加 2 条）

- 加入测试驱动验证（模型结束时自动跑测试，失败把报错交回模型，最多打回 2 次）、工具输出头尾截断与上下文压缩；把 thinking 开关等供应商扩展参数配置化，并记录每次模型调用的 token 和耗时。
- 修复原版命令白名单等 4 处安全漏洞（`conda run` 可执行任意命令、前缀匹配可被绕过、黑名单大小写失效、密钥文件可读且会传给测试进程）；编写 38 个基于假 LLM 的单元测试，离线覆盖 Agent 主循环。

## 四、三条底线

- **数字带口径。** 说"成功率 97.2%"时，要能接着说出"12 个任务、每个跑 3 次、DeepSeek V4.1-Flash、关闭 thinking"。
- **不夸大。** 不写"大幅提升""生产级"；没有触发过的机制（测试驱动验证）不算进提升；没做的东西（沙箱、向量检索、模型摘要）只能说成"设计方案"。
- **和代码一致。** 方法名、模型名、文件名都要和仓库对得上，例如模型是 `deepseek-ai/DeepSeek-V4.1-Flash`，框架是 LangGraph。

## 五、常见追问的应对

| 追问 | 回答要点 | 详见 |
| --- | --- | --- |
| 哪些是你做的，哪些是原项目的？ | 主流程、仓库索引、最初的工具集来自原项目；工具调用协议、测试驱动验证、评测框架、安全修复、单元测试是我做的 | 《改进说明》 |
| 为什么原版成功率这么低？ | 15 次失败全是格式中止：没传 tools 时模型会漏出 DSML 标记，原版解析器找不到 JSON | 《改进说明》第 1 条 |
| function calling 和在 prompt 里要求 JSON 有什么区别？ | 前者由接口保证结构，工具以 schema 声明，结果以 tool 消息回传；后者要自己解析文本，容易被模型自带的格式干扰 | 第四部分 |
| 怎么保证评测可信？ | 任务可解性、非平凡性自动校验；恢复原始测试 + 隐藏测试；三种配置共用同一模型、工具和措辞，逐项叠加 | 第八部分 |
| 测试驱动验证有用吗？ | 这批任务上没被触发，模型都是先测再结束；单元测试证明它能打回提前的 finish，属于兜底 | 《改进说明》第 2 条 |
| 成本变高了吗？ | 单次运行 token 多约 60%，因为多轮消息累积上下文；按每个成功任务算基本持平，约 3.3 万 token | 评测报告 |
| 安全怎么做的？还有什么风险？ | 白名单精确匹配、拒绝 shell 操作符、禁止读写密钥、清除密钥环境变量；pytest 会执行仓库代码，真正的隔离需要沙箱 | 《改进说明》第 6 条 |
| 数据集有什么问题？ | 12 个任务、自建，规模小；DSML 泄漏和具体模型有关；下一步在 SWE-bench 上验证 | README 局限一节 |
