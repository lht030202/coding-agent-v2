# 改进说明：新版相对原版改了什么

本文逐条说明 coding-agent-v2 相对原项目 [Coding-Agent-SFT-Lab](https://github.com/shuailishuaiqiYangLiu/Coding-Agent-SFT-Lab) 的改动。每条都按同一个顺序写：**原版的问题 → 怎么改 → 代码位置 → 怎么验证 → 面试一句话**。

学新版时按本文的顺序读即可。前三条是主线，面试最常被追问。

---

## 1. 工具调用：从解析 JSON 文本改为原生 function calling

**原版的问题。** 原版在 prompt 里要求模型"只输出一个 JSON 对象"，再用正则从回复里抠出 JSON。解析失败就把这一步当成 `finish`，整个任务直接结束。

评测时发现了一个很具体的失败方式：DeepSeek V4.1-Flash 在没有收到 `tools` 参数时，有时会把自己训练时用的原生工具调用标记（`<｜DSML｜ invoke name="read_file">…`）当成普通文本输出。原版解析器找不到 JSON，第一步就中止了。

**怎么改。**
- 九个工具各写一份 JSON Schema（名字、描述、参数类型、必填项），通过接口的 `tools` 参数发给模型。
- 模型返回结构化的 `tool_calls`，格式由接口保证。
- 工具结果以 `role: "tool"` 的消息回传，并用 `tool_call_id` 和对应的调用配对。对话因此变成多轮消息，模型能看到自己之前每一步做了什么。
- 两种异常不再中止任务：参数 JSON 写错时，把错误作为工具结果返回；模型回复纯文本、没调工具时，追加一句提醒让它继续，连续两次才停。
- 原版的 JSON 模式完整保留（`CC_AGENT_TOOL_MODE=json`），用来做对比实验。为了只比较协议，两种模式的工具描述用的是同一套措辞（主评测之后 read_file 又加了行范围参数，两种模式的说明里都补上了，见第 8 条）。

**代码位置。**
- 工具 schema：`src/cc_agent/tools.py:67`（`TOOL_SPECS`）；原版的工具描述原文（只加了 read_file 的行范围参数）：`src/cc_agent/tools.py:117`
- 原生模式的一步：`src/cc_agent/graph.py:350`（`_act_native`）
- 原版模式的一步：`src/cc_agent/graph.py:255`（`_act_json`）
- 解析模型返回的工具调用：`src/cc_agent/llm.py:63`（`chat`）

**怎么验证。** `tests/test_graph.py` 里有"参数 JSON 写错变成观察结果""纯文本回复被提醒""原版模式解析失败即中止"三个用例；评测报告里对比 v0 和 v1 的格式错误次数和成功率。换成 Qwen3-8B 复测时，原版一次格式中止都没有，原生 function calling 的成功率从 22.2% 到 36.1%，提升不显著。再换成更强的 Qwen3.8-27B，三种配置的成功率是 91.7%、94.4%、91.7%，原版 36 次里只有 1 次格式错误。可见主评测里的大幅提升，主要来自修掉 DeepSeek 的 DSML 泄漏这个具体问题（README 补充实验 A、D）：原生 function calling 消除的是格式解析失败这一类故障，收益大小取决于模型出这类故障有多频繁。

**面试一句话。** 原版靠 prompt 约定 JSON 再解析文本，新一代模型按原生工具调用训练，会把自己的格式漏到文本里，导致解析失败、任务中止；改成原生 function calling 后，格式由接口保证，异常也能作为观察结果交回模型处理。换模型复测后发现，收益取决于模型出格式故障的频率：DeepSeek 上 58% → 97%，千问上差距在随机波动范围内。

## 2. 验证：从"只判断停不停"改为"结束前自动跑测试"

**原版的问题。** 原版的 verify 节点只看模型有没有调 `finish`、步数有没有用完，写下的 note 只进日志，模型看不到。模型说"修好了"，流程就结束，哪怕测试还是红的。

**怎么改。** `CC_AGENT_VERIFY_MODE=tests` 时，模型调用 `finish` 后，系统自己运行测试命令：
- 测试通过，进入 review；
- 测试失败，就把测试输出作为一条消息交回模型，让它继续修，最多打回 2 次；
- 步数用完时也会跑一次测试，记录最终状态。

**代码位置。** `src/cc_agent/graph.py:449`（`_verify_with_tests`），打回条件在 `src/cc_agent/graph.py:461`。

**怎么验证。** `tests/test_graph.py::test_failed_finish_is_sent_back_with_the_test_output`（提前 finish 被打回，修好后通过）和 `test_rule_verify_accepts_a_premature_finish`（原版规则接受提前 finish，bug 留在代码里）。评测报告的"测试验证打回"和"被打回后修好"两列。真实运行里：DeepSeek 上打回 0 次，因为模型都是先跑测试再结束；换成更弱的 Qwen3-8B 后打回 4 次，其中 1 次修好通过，而对照组（没有验证）的 2 次同类情况都以失败结束（README 补充实验 A）。

**面试一句话。** 不能信模型自己说的"完成"，验证必须由程序执行：结束前自动跑测试，失败就把报错交回模型，形成闭环。

## 3. 评测：从"没有成功率"到可复现的对比实验

**原版的问题。** 原版没有任务成功率指标，批量运行时的 `ok: True` 只表示程序没报错。README 里"JSON 合法率 0% → 94.6%"那组数字，主要是评测设置造成的（base 模型的 prompt 里没给工具列表和输出格式），不能说明 Agent 修代码的能力。

**怎么改。**
- **任务集**：写了一个小型电商代码库 minishop（定价、优惠券、库存、解析、发票、商品目录共 8 个模块），往正确代码里注入 8 种 bug，每种是一个任务。任务专门针对原版的弱点：正则转义、带引号的字符串、两处修复、跨模块定位、大文件、功能实现。另有 4 道 HumanEval 函数题。
- **任务校验**：`eval/build_tasks.py` 自动检查两件事：正确版本必须通过全部测试（任务可解）；注入 bug 后必须至少有一个可见测试失败（任务不是空的）。这个校验查出原仓库的一道题早已被解好、答案留在题目文件里，已恢复成原题。
- **判定**：Agent 结束后，先恢复原始测试文件（防止改测试作弊），再放入隐藏测试，全部通过才算成功。
- **对比**：三种配置逐项叠加，v0 原版 → v1 加原生 function calling → v2 再加测试驱动验证。每个任务每种配置跑 3 次，统计成功率、步数、token、耗时、格式错误和打回次数。

**代码位置。** `src/cc_agent/evaluation.py`（`prepare_workspace` 第 69 行、`judge` 第 81 行、`run_one` 第 105 行），`eval/task_defs.py`、`eval/build_tasks.py`、`eval/base_repos/`。

**怎么验证。** 运行 `.venv/bin/python run_agent.py eval`，报告写在 `eval/results/<时间>/report.md`。

**面试一句话。** 先定义"成功"——恢复原始测试加隐藏测试，全过才算；再用逐项叠加的配置做消融，每个改进贡献多少都有数字。

## 4. 模型调用层：一个入口管住供应商、参数、重试和成本

**原版的问题。** 只返回回答文本，token 用量被丢掉；thinking 模式默认开着，Agent 每步都在为思考付费；没有超时和重试设置。

**怎么改。**
- 供应商扩展参数配置化：`.env` 里的 `OPENAI_EXTRA_BODY` 原样通过 `extra_body` 传给接口。硅基流动写 `{"enable_thinking": false}`，DeepSeek 官方写 `{"thinking": {"type": "disabled"}}`，代码不用改。
- 每次调用返回 `LLMResult`：文本、工具调用、输入/输出/思考 token、耗时。
- 设置超时，由 SDK 对 429、5xx 和连接错误做指数退避重试。

**代码位置。** `src/cc_agent/llm.py:44`（`OpenAICompatibleChat`），配置解析在 `src/cc_agent/config.py:15`（`parse_extra_body`）。

**面试一句话。** OpenAI 兼容只保证主干字段一致，各家扩展参数不同，所以把扩展参数配置化，统一从一个入口传；同一个入口也负责记录 token 和耗时、处理重试。

## 5. 上下文管理：截断加压缩，不丢配对

**原版的问题。** 每一步只带最近 12 条工具记录，每条按字符硬截断，最后再按总长从中间切开，可能把一行 JSON 切成两半。

**怎么改。**
- 单个工具输出超过 6000 字符时，保留开头和结尾（报错通常在两端），中间省略。
- 整段对话超过字符预算时，把较早的工具输出压缩成短预览。消息一条都不删，因为每个工具调用都必须和它的结果配对，删了接口会报错。

**代码位置。** `src/cc_agent/context.py:7`（`truncate_middle`）、`src/cc_agent/context.py:21`（`compact_messages`）。

**实测。** 主评测里压缩一次都没触发（单次调用最长约 9.8k token）。把预算降到 2 万字符后，36 次运行里有 10 次触发了压缩，成功率基本不变，但 token 也没省下来：触发压缩的运行反而多走了几步。在平均 4～5 步的短任务上压缩不划算，它的作用是在长任务里防止上下文超出模型窗口（README 补充实验 B）。

**修复（实验 B 之后发现）。** 压缩后的消息会写回对话状态，而"预览 + 标记"仍超过 400 字符的阈值，所以后面每一步都会把同一条消息再压一次：计数重复（实验 B 报告里的 38 次偏高），预览末尾还会叠加标记、挤掉原来保留的尾部内容。模拟 8 次工具调用，计数是 15，最早那条消息叠了 5 个标记。现在已压缩过的消息不再处理，`tests/test_context.py::test_compacted_messages_are_left_alone_on_later_steps` 覆盖这一点。实验 B 是修复前跑的。

**还没做（设计）。** 用模型把早期对话总结成摘要。

**面试一句话。** 多轮工具调用的消息不能随便删，否则调用和结果对不上；所以只压缩旧的工具输出内容，保留最近几轮原文。

## 6. 安全边界：修掉原版 hooks 的四个漏洞

**原版的问题。**
1. 测试命令白名单里有 `conda run`，`conda run -n base <任意命令>` 能直接执行任意程序；
2. 白名单按字符串前缀匹配，`pytest_evil` 也能通过；
3. 黑名单里 `chmod -R 777` 带大写字母，和转成小写的命令比较，永远匹配不上；
4. `.env` 只禁止修改、不禁止读取，测试子进程还会继承 API key，一个打印环境变量的测试就能把 key 泄露进上下文和轨迹。

**怎么改。** 白名单改成按 token 精确匹配前缀，并删掉 `conda run`；拒绝 `;`、`&&`、`|` 这类 shell 操作符；黑名单统一小写比较；禁止读写 `.env*`、私钥等文件（`.env.example` 这类模板除外），grep 也会跳过它们；运行测试前清除名字里带 KEY、TOKEN、SECRET、PASSWORD 的环境变量。

**代码位置。** `src/cc_agent/hooks.py:27`（白名单）、`:55`（受保护文件）、`:87`（命令校验）、`:108`（清除密钥）。

**还没做（设计）。** pytest 会执行仓库里的代码（例如 `conftest.py`），hooks 挡不住，真正的隔离需要 Docker 沙箱。

**面试一句话。** prompt 不是权限系统，命令校验要用白名单精确匹配；但只要会执行仓库代码，就必须靠沙箱隔离，hooks 只是第一道防线。

---

## 7. 工程质量：单元测试和可观测性

- **单元测试**：43 个，用一个按剧本回复的假模型（`tests/helpers.py` 的 `ScriptedLLM`）测试 Agent 主循环，不调用真实模型，结果可重复、零成本。运行：`.venv/bin/python -m pytest -q`。
- **CI**：`.github/workflows/ci.yml`。每次推送到 main 或提交 PR，GitHub Actions 都会在 Python 3.10（`requires-python` 的下限）和 3.12 上装好依赖，运行 ruff 代码检查和全部单元测试；测试用假模型，不需要 API 密钥。`eval/tasks` 下是故意注入 bug 的任务仓库，不参与代码检查。
- **可观测性**：每次模型调用在轨迹里写一条 `llm_call`（节点、token、耗时），任务结束写 `run_summary`（步数、结束原因、测试结果、token 合计）。`run_agent.py stats` 汇总所有轨迹。
- **轨迹文件名**：加了微秒和随机后缀，并行评测时不会写进同一个文件。

## 8. 大文件读取：read_file 按行分页（从评测轨迹里发现的问题）

**问题（新版自己的）。** 统计 108 次评测运行的轨迹时发现，两个机制互相冲突：read_file 只能从文件开头往后读，默认最多 12000 字符；原生模式下，工具输出又会被截到 6000 字符、只留头尾（第 5 条）。大文件任务 ms08 里，模型请求读完 15k 字符的商品目录，实际只看到了头尾各 3000 字符。read_file 的提示让它"传更大的 limit"，可传了也没用。

**怎么改。**
- read_file 新增 `start_line` / `end_line`（从 1 开始，含尾行），可以配合 grep 给出的行号直接读文件中段；指定范围时，输出开头标出 `[lines a-b of N]`。
- 读出的内容控制在工具输出预算（默认 6000 字符）减 400 字符以内，上下文层就不会再从中间截掉文件内容。超出时停在整行，并提示从第几行接着读，或者用 grep 定位。
- 单行过长时截断并提示用 grep；`start_line` 超过文件末尾时返回错误观察。

**代码位置。** `src/cc_agent/tools.py:222`（`_read_file`），工具输出预算由 `src/cc_agent/graph.py:153`（`_tools`）传入；参数说明在 `src/cc_agent/tools.py:67`（原生工具定义）和 `:117`（v0 的文本说明）。

**怎么验证。** `tests/test_tools.py` 新增 3 个用例：按行范围读取、长文件分页且输出不超过预算、起始行越界。复跑 ms08 三次，模型每次都直接按符号索引的行号读第 270–330 行，每次运行的 token 从 47.0k 降到 31.2k，步数从 5 降到 4（README 补充实验 C）。

**补充：v0 的文本说明漏改了（Qwen3.8-27B 评测里发现）。** 最初只给原生工具定义加了 `start_line`，v0 用的文本协议说明还是原文。用 Qwen3.8-27B 跑三种配置时，v0 在 ms08 上平均 66.8k token，3 次里有 2 次把 10 步用完，反复读第一页、反复 grep。分页提示"Read on with start_line=118"在输出末尾，而 v0 每步重拼 prompt 时，每条工具输出只保留前 1800 个字符（`src/cc_agent/graph.py:83`，`_history_text`），提示被截掉了，说明里又没写这个参数，模型无从知道还能按行读。在 v0 的说明里补上可选的 `start_line` / `end_line` 后复跑 3 次，每次第一步就按符号索引的行号读 `price_range` 附近（两次第 285–320 行，一次第 300–320 行），平均 25.9k token、4 步（README 补充实验 D）。工具输出可能被截断，写在输出里的提示不一定能被模型看到，参数必须写进工具说明。新增回归测试 `tests/test_tools.py::test_both_protocols_document_the_line_range`，防止两套说明再次不一致。

**面试一句话。** 评测轨迹里发现两个机制打架：工具输出截头尾是为了看清报错，却让大文件的中间部分读不到；改成按行分页后，模型可以拿 grep 给出的行号精确读取。另外，工具说明就是模型的接口文档：工具输出可能被截断，新参数只写在输出提示里，模型可能根本看不到。

---

## 没改的部分

- LangGraph 的主流程（index → plan → act ⇄ verify → review → summarize）保持不变。
- 仓库索引和关键词检索（`repo_indexer.py`）保持不变。
- review 仍然不能把任务打回，这一条属于【设计】。
- 原项目的 SFT 训练部分（数据构建、LLaMA-Factory、Qwen3-8B LoRA）没有带过来。
