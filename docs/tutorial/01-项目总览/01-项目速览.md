# 项目速览

> **三分钟建立整体认知。** 读完本文，你应当能用一两句话说明：这个项目在解决什么问题，采用什么思路，现在做到了哪一步，接下来要改进什么。细节留给后续各部分展开。

**一句话概括：** 给它一个代码仓库和一句任务描述，它会自己读代码、改文件、跑测试，最后审查并总结。可以把它理解成一个迷你版的 Claude Code。

**项目来源：** 本项目基于开源项目 Coding-Agent-SFT-Lab 二次开发。原项目还包含模型微调（SFT）部分，本项目只做 Agent 部分。

---

## 一、项目要解决的问题

### 1.1 大模型会写代码，但不会"干活"

直接让聊天机器人"帮我修这个 bug"，它能给出一段代码，但剩下的事全要你自己做：

- 它看不到你的仓库，你得手动把相关代码贴给它；
- 它改不了文件，你得手动复制粘贴；
- 它不会跑测试，不知道自己改对了没有。

这种用法可以概括为**"模型出主意，人来跑腿"**。

### 1.2 修一个 bug 要走哪几步

拆开看，开发者修一个 bug 大致要走五步，每一步都需要不同的能力。

| 步骤 | 开发者怎么做 | 需要的能力 |
| --- | --- | --- |
| 了解仓库 | 看目录结构、搜索代码 | 列文件、搜索 |
| 定位问题 | 读相关代码和测试 | 读文件 |
| 修改代码 | 改几行，或者重写文件 | 编辑文件 |
| 验证 | 跑测试 | 执行命令 |
| 收尾 | 自查一遍，写说明 | 审查、总结 |

这五步不是一次想好就能做完的：读完代码才知道该改哪里，跑完测试才知道改对没有。**每一步的结果，决定下一步做什么。**

### 1.3 让模型自己干活的三个难点

**其一，多步决策。** 模型要根据上一步的结果决定下一步，而不是一次性生成全部答案。

**其二，动手能力。** 模型只会输出文字。读文件、改代码、跑测试，都得由程序代为执行，再把结果交还给模型。

**其三，风险控制。** 让模型在你的电脑上改文件、跑命令，就必须防止它越界，比如改仓库外的文件、执行删除命令。

> 三个难点指向同一个结论：需要用一个"循环 + 工具 + 安全边界"的程序把模型包起来。这个程序就是 Coding Agent。

## 二、项目的处理思路

本项目的核心思路可以概括为：**模型做决定，程序去执行，结果再交回模型**，如此循环，直到任务完成。

这有点像远程指导装修：师傅（模型）不在现场，只能打电话下指令，比如"打开那面墙看看""把这根水管换掉""开水试试漏不漏"；工人（程序）照做，再把现场情况拍给师傅看；师傅看完，决定下一步。工人还有自己的规矩：只在这一户干活，危险的活一律不接。

### 2.1 主流程：六个节点

整个流程用 LangGraph 编排成一张图，包含六个节点。

| 节点 | 做什么 | 调模型吗 |
| --- | --- | --- |
| index_repo | 扫描仓库，整理出文件树、函数列表和相关代码片段 | 否 |
| plan | 写一份修复计划 | 是 |
| act | 每次选一个工具并执行；这是核心，最多走 8 步 | 是，每步一次 |
| verify | 判断要不要继续：调了 finish 或步数用完就停 | 否 |
| review | 换成"审查员"角色，检查任务是否真的完成 | 是 |
| summarize | 写最终总结 | 是 |

其中 act 和 verify 构成一个循环：act 执行一步，verify 判断没完成，就回到 act 再走一步。

### 2.2 工具层：九个工具

模型在 act 里每次选一个工具。九个工具按用途分成四类。

| 类别 | 工具 |
| --- | --- |
| 看 | `list_files`、`read_file`、`grep`、`retrieve_context` |
| 改 | `replace_in_file`（精确替换，要求旧文本只出现一处）、`write_file`（整个文件重写） |
| 验 | `run_tests`、`git_diff` |
| 停 | `finish` |

原版的调用方式是：模型输出一段 JSON 文本，比如 `{"tool": "read_file", "arguments": {"path": "calculator.py"}}`，程序把它解析出来再执行。新版改成**原生 function calling**：九个工具以 JSON Schema 的形式发给接口，模型直接返回结构化的工具调用，执行结果作为 `tool` 消息回传。无论哪种方式，工具执行出错都不会让程序崩溃，而是把错误信息交还给模型，让它自己调整。

### 2.3 安全层：执行前先检查

每个工具执行之前，都要先过一道检查（hooks）：

- 路径必须在仓库目录里面；
- 测试命令必须以 `pytest` 等白名单开头，并且不含 `rm -rf` 这类危险片段；
- 不允许修改 `.env`、私钥这类敏感文件。

每一步做了什么，都会写进 `traces/` 目录下的轨迹文件。

> 原版这一层有四个漏洞，比如白名单里的 `conda run` 可以用来执行任意命令，新版都已修复（见《改进说明》第 6 条）。不过 pytest 会执行仓库里的代码，真正可靠的隔离要靠沙箱，这在本项目里属于【设计】，没有实现。

## 三、新版做到了什么

### 3.1 改了哪些地方

| 原版的短板 | 新版的做法 | 状态 |
| --- | --- | --- |
| 工具调用靠解析文本，格式一出错任务就结束 | 原生 function calling；参数错误、纯文本回复都交回模型处理 | 【改进】 |
| 没有任务成功率指标 | 12 个任务的评测框架：恢复原始测试 + 隐藏测试判定，三种配置逐项对比 | 【改进】 |
| verify 只判断停不停 | 模型结束时自动跑测试，失败就把报错交回模型 | 【改进】 |
| 不记录 token 和耗时；thinking 默认开着 | 扩展参数配置化（关闭 thinking）；每次调用记录 token 和耗时 | 【改进】 |
| 上下文按字符硬截断 | 多轮消息；工具输出保留头尾；超预算时压缩旧输出 | 【改进】 |
| hooks 有四个漏洞 | 全部修复 | 【改进】 |
| 没有单元测试 | 38 个，用假模型离线测试主循环 | 【改进】 |
| review 不能打回、没有沙箱、模型摘要、向量检索 | 只有方案 | 【设计】 |

### 3.2 评测结果

口径：12 个任务（8 个多文件仓库任务 + 4 道函数题），每个任务在每种配置下跑 3 次；模型为硅基流动的 `deepseek-ai/DeepSeek-V4.1-Flash`，关闭 thinking，最多 10 步；2026-11-09 测量。

| 配置 | 总成功率 | 多文件仓库任务 | 因格式问题中止 | 每个成功任务的 token |
| --- | --- | --- | --- | --- |
| v0 原版 | 58.3% | 37.5% | 15 次 | 33.8k |
| v1 + 原生 function calling | **97.2%** | **100%** | **0** | 33.0k |
| v2 + 测试驱动验证 | 97.2% | 100% | 0 | 31.7k |

三点要能讲清楚：

1. **提升来自工具调用协议。** 原版失败的 15 次全是同一个原因：请求里不带 `tools` 时，模型把自己原生的工具调用标记（DSML）当成文本输出，解析器找不到 JSON，任务中止。
2. **测试驱动验证没有被触发。** 原生模式下，模型都是先跑测试再结束，所以 v2 和 v1 的成功率一样。它是兜底机制，不能算进提升。
3. **成本基本持平。** 单次运行的 token 多了约 60%，但按每个成功任务算，三者都在 3.3 万 token 左右。

> 先定下"测什么、怎么测"，再动手改进，改进前后的数字才有可比性。
